# SLSA: what this pipeline produces, and what it does not

SLSA (Supply-chain Levels for Software Artifacts) is a framework for answering one question: *how much can you trust
the claim that this artifact came from that source, built that way?* This document maps each SLSA requirement to a
concrete artifact you can fetch from the registry today, and is honest about the gaps.

## Three different claims, often confused

| Artifact | Answers | Produced by |
|---|---|---|
| **Signature** | *Who built this?* | `cosign sign` — keyless, identity from GitHub OIDC |
| **SBOM** | *What is inside it?* | Syft → SPDX JSON, attached with `cosign attest --type spdxjson` |
| **Provenance** | *How was it built — from which commit, by which workflow?* | `actions/attest-build-provenance` |

A signature without an SBOM tells you a trusted party built an opaque box. An SBOM without a signature is a text
file anyone can rewrite. Provenance is what ties the box to the commit that produced it. The pipeline emits all
three, and the `verify` job fails the build if any is missing.

## Why keyless

Traditional signing needs a private key: stored somewhere, rotated on a schedule, and catastrophic when leaked —
because a leaked key signs *anything*, retroactively, and revocation depends on everyone checking a revocation list.

Keyless signing inverts it. At signing time the workflow presents its OIDC token to **Fulcio**, which issues a
certificate valid for ten minutes bound to that identity
(`https://github.com/slackerwx/<repo>/.github/workflows/<file>@refs/heads/main`). The signature and the certificate
are recorded in **Rekor**, a public append-only transparency log. Verification does not ask "was this signed with
the right key?" but "was this signed by the right *identity*, and is that entry in the log?"

There is no key to steal. An attacker who wants a signature Kyverno accepts must get code to run inside a `slackerwx`
workflow on `main` — which is a branch-protection problem, not a secret-management problem, and that is a much better
problem to have.

## SLSA build levels, and where we sit

| Level | Requires | Us |
|---|---|---|
| **L1** | Provenance exists and is available | ✅ `attest-build-provenance`, pushed to the registry next to the image |
| **L2** | Provenance is signed, generated by a hosted build service | ✅ signed via Sigstore, generated by GitHub-hosted runners; the build is not attacker-controllable from the workflow file alone |
| **L3** | Provenance generated by a **hardened, isolated** builder the build itself cannot forge | ❌ our provenance is produced by a step in the same job as the build |
| **L4** | (Retired in SLSA v1.0; the old two-party-review/hermetic tier) | n/a |

We claim **L2**, verifiably. The honest L3 gap: `actions/attest-build-provenance` runs in the same job as
`docker/build-push-action`, so a compromised build step is in a position to influence what the provenance says about
itself. Reaching L3 means `slsa-framework/slsa-github-generator`, which builds inside a separate, pinned reusable
workflow the caller cannot modify. It was evaluated and deferred: it adds a second build path and considerably more
machinery than a homelab pillar needs, and it does not change the Kyverno admission story at all. It stays in the
backlog with this document as the argument.

## The evidence map

Given an image reference `ghcr.io/slackerwx/<name>@sha256:<digest>`:

| Claim | How to check it | What proves it |
|---|---|---|
| Built by a slackerwx workflow on `main` | `cosign verify --certificate-oidc-issuer … --certificate-identity-regexp …` | Fulcio certificate + Rekor entry |
| Contents are declared | `cosign verify-attestation --type spdxjson …` | signed in-toto statement wrapping an SPDX document |
| Contents were scanned | Grype SARIF in the GitHub Security tab; the build fails above the gate | workflow run + SARIF |
| Built from a specific commit | `gh attestation verify oci://… --owner slackerwx` | SLSA provenance predicate (`buildDefinition.resolvedDependencies`) |
| The whole set is present | the `verify` job of `reusable-container.yml` | a separate job with its own narrow permissions |

`scripts/verify-image.sh` runs the first, second and fourth rows in one shot.

## Reading a provenance statement

```bash
gh attestation verify oci://ghcr.io/slackerwx/platform-supply-chain-hello@sha256:<digest> \
  --owner slackerwx --format json | jq '.[0].verificationResult.statement.predicate'
```

The fields that matter to an auditor:

- `buildDefinition.buildType` — the recipe format (`https://actions.github.io/buildtypes/workflow/v1`)
- `buildDefinition.externalParameters.workflow` — repository, path and ref of the workflow that built it
- `buildDefinition.resolvedDependencies[].digest` — the **exact commit** of the source
- `runDetails.builder.id` — the builder identity; for L3 this is what would have to be an isolated builder
- `runDetails.metadata.invocationId` — the run URL, so a human can open the logs

## How an auditor verifies without trusting us

Every step below can be performed by someone with no access to the homelab, no credentials of ours (beyond read
access to a private package) and no reason to believe anything we say:

1. Fetch the image by digest — a digest is content-addressed, so nothing can be swapped underneath.
2. `cosign verify` with an identity regexp **they** choose. It fails unless the certificate really was issued to a
   `slackerwx` workflow on `main`.
3. Look the entry up in Rekor (`rekor-cli search --sha <digest>`). Rekor is a public log we do not operate; an entry
   there proves the signature existed at a point in time and was never quietly replaced.
4. `cosign verify-attestation --type spdxjson` and read the SBOM. Compare the package list with what the Dockerfile
   claims to install.
5. `gh attestation verify` and read `resolvedDependencies` — then go read that commit on GitHub.

At no point does the auditor have to take our word for anything. That is the entire product.

## Known limits

- **Rekor is public, the packages are private.** The transparency log entry reveals that
  `ghcr.io/slackerwx/<name>@sha256:…` was signed, and by which workflow. The image contents stay private; the
  *existence* and identity do not. Acceptable here, worth knowing before applying this pattern to a secret project.
- **The gate is `critical` by default.** A HIGH CVE ships. The SARIF records it and `docs/runbook.md` covers
  triage; the decision is deliberate, not an oversight.
- **A signature is not a safety certificate.** It says who built the artifact, not that the artifact is good. Signed
  malware is still malware — the value is that it is *attributable* malware.
